一台远程电脑在管理页面里明确显示 connected，运行在它上面的 Agent 却一直报连接被拒绝。

第一反应很容易是：“电脑离线了。”

这次我也这么判断了，因为一次点对点 ping 超时。但这个结论是错的。重新核对后，电脑在线，组网客户端在线，真正断掉的是更上层的应用入口。

**远程系统里的“在线”不是一个布尔值，而是一组分层状态。**

## 🧱 先拆成四层，不要一句“在线”包打天下

一条常见的远程 Agent 链路至少包含四层：

1. **设备层**：电脑是否开机，系统是否正常运行？
2. **组网层**：Tailscale、ZeroTier 等客户端是否登录并保持连接？
3. **入口层**：反向代理、Serve 路由或监听端口是否存在？
4. **应用层**：远程 Agent 是否连接到网关，并能执行真实请求？

这四层可以出现“下层正常、上层失败”的组合：

- 设备与组网在线，不代表 443 入口还在；
- 入口返回 HTTP，不代表 Agent 已认证回连；
- Agent 显示 connected，也不代表真实远程命令一定成功。

因此，“在线吗”必须改写成可验证的问题：**哪一层在线，哪一层失败？**

## ⚠️ 单次 ping 是弱证据，不能覆盖完整状态

ping 超时可能来自中继路径、ICMP 行为、临时抖动或探测窗口。它能证明“这一次探测没有收到回复”，却不能单独证明设备关机。

更可靠的判断需要组合证据：

- 管理面是否仍显示 active；
- 客户端状态是否有近期收发流量；
- 目标端口是超时、拒绝连接，还是成功握手；
- 应用自身是否报告连接；
- 最终能否完成一条最小真实请求。

尤其要区分两种网络错误：

- **timeout**：路径上没有及时响应，原因仍然很多；
- **connection refused**：目标地址可达，但对应端口没有服务接受连接。

当远端反复连接某个固定入口并收到 `ECONNREFUSED`，而网关本地端口仍健康时，优先检查入口发布是否消失，而不是先宣判整台设备离线。

## 🔍 “故障点”不等于“为什么故障”

排查过程中还有一个容易混淆的层次：直接故障与底层触发原因。

这次可以先闭环的直接故障是：

> Serve 路由退出 → 对外端口消失 → 远程 Agent 无法连接。

但这还没有回答路由为什么退出。继续按时间线对齐应用日志、系统日志与更新器记录后，才找到底层触发链：

> 组网客户端自动更新并重启 → 路由持有进程随之退出 → 网关只记录告警，没有重新发布路由。

在找到更新事件前，把“路由退出”直接叫作根因，会显得结论已经完整，实际上只是定位了断点。

更准确的表达应该是：

- **已确认**：直接故障发生在入口层；
- **待查**：是什么生命周期事件让入口退出；
- **查实后**：自动更新触发退出，而网关缺少恢复机制，使短暂重启变成永久故障。

这种分层能阻止“一个合理解释”过早变成事实。

## 🛠️ 自愈要有门槛，不是发现异常就重启

入口消失后，最粗暴的方案是定时重启网关。但没有门槛的自动重启只是把故障升级成重启循环。

一个可控的自愈器至少需要：

- 确认组网客户端在线；
- 确认网关本地健康；
- 连续多次确认入口缺失，过滤瞬时抖动；
- 设置冷却时间与单位时间重启上限；
- 前置条件未知时保持不动作；
- 重启后验证入口、Agent 回连和真实命令；
- 连续失败时停止自动操作，只记录并报警。

这里的关键不是“会重启”，而是**知道什么时候不该重启，并能证明恢复真的完成**。

## 🧪 真环境会暴露测试夹具看不到的问题

本地测试全部通过后，第一次自然触发仍暴露了两个环境差异：

1. LaunchAgent 的 PATH 比交互式 shell 精简，命令入口能找到，解释器却不一定能找到；
2. 新版本客户端的状态 JSON 增加了一层包装，旧解析器把健康状态误判为缺失。

这两类问题都说明，验收不能停在“脚本手动运行成功”。至少还要覆盖：

- 由真实调度器启动；
- 在真实环境变量下执行；
- 等待真实故障条件自然累积；
- 完成一次自动恢复；
- 再观察两轮以上健康稳态，确认不会误触发。

**自然触发测试验证的是整条生命周期，手动冒烟只验证了其中一个瞬间。**

## ✅ 远程链路的最小验收顺序

可以把验收固定成从底到上的五步：

1. 设备和组网客户端显示在线，并有近期流量；
2. 入口路由存在，目标端口可连接；
3. HTTPS 或协议探针返回预期结果；
4. 远程 Agent 状态变为 connected；
5. 执行一条只读真实命令，核对返回值。

最后一步不可省。状态页和健康接口都是系统自报，真实请求才是用户真正依赖的结果。

这次最重要的教训不是某个组网产品如何配置，而是：**把“在线”拆成层，把证据按强弱排序，把故障点与触发原因分开，再让自愈接受真实生命周期验收。**
