一个维护脚本原本只负责刷新登录二维码。它需要一个已经在运行的网络出口，于是脚本顺手执行了：

```bash
docker compose -f compose.yaml -f compose.egress.yaml up -d egress
```

主服务平时却不是用这组文件启动的。它还叠加了消息桥接、代理和其他服务配置。

结果，Compose 根据维护命令眼前的文件集合重新计算项目状态，认为共享出口需要重建。这个动作又影响了依赖它的主应用和消息桥接；脚本只确认二维码出来了，却没有确认业务服务是否还活着。一个看起来局部的扫码动作，最终造成整套后台中断。

根因不是 Docker 偶发抽风，而是：**同一个 Compose project 被两套不一致的拓扑定义管理。**

## 🔍 Compose 操作的边界是 project，不是命令里写的服务名

看到下面的命令，人很容易理解为「只处理 egress」：

```bash
docker compose up -d egress
```

但 Compose 不只是启动一个容器。它会读取当前文件集合、环境变量和 project name，生成期望状态，再拿这个状态与现有项目比较。

如果维护脚本少带了某个 override 文件，或者使用了不同的环境变量，那么它看到的并不是主部署正在运行的完整拓扑。即使目标服务名相同，网络、挂载、依赖、标签或配置哈希也可能不同。Compose 因此有理由重建服务；而重建共享依赖可能波及整条依赖链。

所以命令里的服务名只限定了直接目标，**不能证明副作用也只落在这个服务上。**

## 🧨 共享依赖最危险

数据库、反向代理、出口网关、消息总线这类服务通常被多个业务容器依赖。它们一旦重建，风险不止是短暂断连：

- 依赖容器可能被停止，却没有被当前命令重新拉起；
- 代理仍缓存旧容器 IP，主应用恢复后继续返回 502；
- 消息通道表面在线，实际调用主应用持续失败；
- 维护脚本自己的目标完成了，于是以 0 退出，制造「操作成功」假象。

这类事故尤其隐蔽，因为局部检查往往全部通过：二维码生成了、目标容器是 running、命令退出码也是 0。坏掉的是脚本没有检查的业务链路。

## 🛠 正确做法：拓扑只有一个装配入口

最稳的办法不是在每个脚本里手写一串 `-f`，而是把完整文件集合收敛到一个入口：

```bash
compose() {
  docker compose \
    -f compose.yaml \
    -f compose.proxy.yaml \
    -f compose.egress.yaml \
    -f compose.messaging.yaml \
    "$@"
}
```

部署、升级、登录维护和故障恢复都调用同一个入口。这样文件顺序、project name 和环境来源不会漂移。

如果维护动作只要求「共享依赖已经存在」，更安全的策略是：

1. 先检查目标容器是否已运行且健康；
2. 已健康就完全不动它；
3. 只有确实不存在时，才通过统一装配入口创建；
4. 不允许维护脚本用自己的简化拓扑覆盖主部署状态。

换句话说，**能复用现有运行态，就不要为了幂等外观强行执行一次 `up`。** `up -d` 不是无副作用的查询。

## ✅ 完成条件必须覆盖业务链路

维护脚本不能以「二维码已生成」或「目标容器 running」作为唯一成功条件。它至少还应验证：

```text
主应用健康
消息桥接健康
反向代理入口返回预期状态
关键 API 可达
维护目标本身完成
```

如果操作可能重建代理或上游容器，还要重新检查代理是否拿到了新地址。容器恢复并不自动等于代理链路恢复。

更进一步，可以在执行前后保存运行容器集合，并拒绝出现非预期减少：

```bash
before=$(docker compose ps --services --status running | sort)
# maintenance action
after=$(docker compose ps --services --status running | sort)
diff -u <(printf '%s\n' "$before") <(printf '%s\n' "$after")
```

这不能代替业务探针，但能快速发现「为了维护 A，顺手停了 B」。

## 一句话

**同一个 Compose project 只能有一套权威拓扑。维护命令若用简化配置重新解释它，局部动作就可能升级成全局事故；验收也必须看业务链路，而不是只看目标容器。**
