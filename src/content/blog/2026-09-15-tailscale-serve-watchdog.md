远程节点断连时，最容易得出的结论是「对端机器离线了」或「Node 没有自启动」。这两个判断都很直觉，也都可能完全错。

我最近处理的一次故障就是这样：远端电脑在线，Tailscale 管理面显示 connected，Node 进程也在反复重连；真正消失的是本机通过 Tailscale Serve 发布的 HTTPS 入口。入口没了，Node 启动得再勤快也只能持续撞向一个不存在的端口。

这次故障最有价值的不是某条修复命令，而是一套可以复用的排查与自愈方法。

## 先把「在线」拆成四层

远程控制链路至少有四个彼此独立的状态：

1. **电脑在线**：操作系统是否运行；
2. **虚拟网络在线**：Tailscale 客户端是否连接控制面并拥有地址；
3. **服务入口在线**：Serve 是否仍把公网或 Tailnet 入口转发到本地服务；
4. **业务节点在线**：远端 Node 是否成功连到 Gateway，并能执行最小只读命令。

单次 `ping` 超时最多只能说明这一次探测没有收到响应。它不能证明电脑关机，更不能证明业务节点没有运行。反过来也一样：管理面显示设备 connected，只能证明虚拟网络层在线，不能证明 Serve 路由或业务连接正常。

因此，排查时不要问一个含糊的「它在线吗」，而要分别回答四个问题。**状态不分层，证据就会互相冒充。**

## 直接故障与触发原因不是一回事

当远端日志持续出现连接被拒绝，而本地 Gateway 仍正常监听时，应该检查请求真正经过的入口。如果 Serve 状态中已经没有目标路由，那么直接故障很清楚：

> 远端 Node 正在运行，但它依赖的 Serve 入口已经消失。

这仍然不是完整根因。继续沿故障发生时间检查系统事件，才能找到触发链：Tailscale 客户端自动更新，应用和网络扩展重启；持有前台 Serve route 的进程退出；上层应用记录入口不可用，却没有重新发布路由。于是一次短暂更新变成了永久断连，直到 Gateway 被人工重启。

这里必须区分两层：

- **直接故障**：Serve 路由消失；
- **底层触发原因**：客户端更新使 route-owner 退出，而上层缺少重新发布机制。

只修直接故障可以恢复一次；找到触发原因，才能设计不会制造新事故的恢复策略。

## 为什么不该直接「失败就重启」

最粗暴的 watchdog（看门狗）会每分钟检查一次，失败就重启 Gateway。它看似积极，实际上可能在网络抖动、客户端升级或本地服务启动期间制造重启风暴。

一个合格的自愈器至少需要这些约束：

- Tailscale 本身在线；
- Gateway 的本地健康检查通过；
- Serve 路由连续多次缺失，而不是单次采样异常；
- 两次恢复动作之间有冷却期；
- 单位时间内设置最大重启次数；
- 状态写入采用原子方式，避免进程中断后留下半份记录；
- 任一前置条件不成立时只记录，不动作。

这套设计的关键不是「自动重启」，而是**只在证据足够时，把恢复动作限制在最小范围内**。

## Staging 通过，不等于真实环境通过

脚本的 fixture 测试、语法检查和 plist 校验全部通过后，我仍在真实 LaunchAgent 环境里撞到两个问题。

第一个是 PATH。交互式终端能找到 Node，不代表 LaunchAgent 也能找到。依赖 `#!/usr/bin/env node` 的 CLI 在精简 PATH 下会直接退出。系统任务应使用明确、稳定的可执行文件路径，不能默认继承人的 shell 环境。

第二个是数据结构漂移。新版 Tailscale 的 Serve 健康 JSON 多了一层包装，测试夹具仍按旧结构解析，导致已经恢复的路由继续被判为缺失。若没有冷却和限流，这个误判会反复触发重启。

所以「测试通过」只能证明测试覆盖的世界成立。上线前还必须让它在真正的调度器、真正的环境变量和真正的命令输出上运行。

## 验收必须穿透整条链路

一个恢复动作执行成功，不代表服务已经恢复。完整验收应依次拿到这些证据：

1. watchdog 连续识别到 Serve 缺失；
2. Gateway 恢复动作返回成功；
3. Serve 路由重新出现；
4. HTTPS 入口返回预期状态；
5. 远端 Node 自动回连；
6. 最小只读远程命令得到正确结果；
7. 后续多轮健康检查保持稳定，且没有重复重启。

其中最后一步很容易被忽略。能恢复一次只说明恢复路径可用；恢复后不再误动作，才说明 watchdog 自己没有成为新的故障源。

## 最后记住三句话

- **单次探测失败不是离线结论。**
- **进程在运行，不代表它依赖的入口还存在。**
- **自愈不是无脑重启，而是证据门控、冷却限流和端到端验收。**

可靠性问题很少靠一条神奇命令解决。真正有效的是把链路拆开，把事实和推论分开，再让自动化只对已经证实的故障负责。
