一个接入 Agent SDK 的 Telegram bot，最初用的是很常见的互斥逻辑：只要当前任务还在运行，新消息就直接拒绝，提示用户等上一项任务结束。

这保证了不会并发启动两个 agent，却牺牲了长任务里最重要的一种交互：**用户无法在任务执行途中补充条件、纠正方向或收紧范围。**

把新消息排到下一个任务，也不完全对。用户说“按钮改小一点”，通常是在修正眼前这项工作，不是在创建一个与上下文脱节的新任务。

要支持真正的“任务中插话”，不能只把拒绝改成排队。它本质上是一次输入模型和生命周期模型的共同改造。

## 📨 流式输入解决“怎么送进去”

一次性调用通常在启动时就把 prompt 固定了。任务开始之后，再收到的消息没有入口进入当前回合。

改成流式输入后，bot 可以在 agent 运行期间继续提交新消息。插话消息使用“下一个可处理时机”的优先级，让 CLI 在完成当前工具调用后，将补充指令并入当前任务。

这个语义很重要：

- 不粗暴打断正在执行的工具调用；
- 不等待整个任务结束；
- 不另开一个缺少上下文的新任务；
- 在 agent 下一次安全取消息时交付。

因此，流式输入解决的是**传输通道**，不是完整的并发安全。

## 🚦 任务结束必须有权威信号

实现过程中最容易犯的错，是把“SDK 调用返回”“收到了最后一段文本”或“本地 Promise resolve”当成任务已经彻底空闲。

这些信号可能早于底层会话真正结束。尤其当 agent 还在收尾、处理工具结果或切换状态时，bot 如果提前开放入口，就会把新消息送入一个正在退出的会话。

更稳妥的做法，是监听 SDK 提供的会话状态事件，并只把明确的 `idle` 视为任务收尾的权威信号。若该事件需要环境开关才能发出，就必须把开关作为运行时契约的一部分，而不是依赖默认行为。

可以把状态机简化成：

```text
idle → running → stopping → idle
          ↑
      接受插话
```

关键不是状态名，而是每个入口都有清晰门控：

- `idle`：新消息启动新任务；
- `running`：新消息进入当前任务的流式输入；
- `stopping`：拒绝或暂存，绝不能再投递给旧任务。

## 🧨 abort 后还有一个短暂竞态

测试时出现了一个很隐蔽的问题：用户执行停止操作后，底层任务不会在同一瞬间完全退出。在这段很短的窗口内，新消息仍可能被流式输入接收。

结果是消息表面上“发送成功”，实际上进入了一个已经决定终止的任务，随后随会话退出一起丢失。

这比明确拒绝更糟，因为用户不知道自己的指令没有被处理。

修复原则很直接：**abort 是业务状态切换，不只是一次底层 API 调用。** 一旦触发 abort，应用层必须立即关闭当前任务的插话入口，不再等待底层进程自然退出。

```text
收到停止命令
  → 立即标记 stopping / aborted
  → 关闭当前流式输入入口
  → 请求底层终止
  → 等待权威 idle 信号
  → 恢复新任务入口
```

这道门能消除“正在退出但仍可写入”的灰色窗口。

## 🧪 验收不能只测顺路径

“任务运行时发一句补充要求，agent 能收到”只能证明最基础的通道打通。完整验收至少要覆盖：

1. agent 正在输出文本时插话；
2. agent 正在执行工具时插话；
3. 连续发送两条补充指令，顺序不乱；
4. 停止后立刻发新消息，不进入旧任务；
5. 等待人工审批时插话，消息不会绕过审批或被吞；
6. 任务自然结束后，下一条消息能正常启动新任务。

其中最值得警惕的是停止窗口和审批窗口。它们都不是普通的 `running`，却很容易被一个简单的布尔变量误判。

## ✅ 结论

任务中插话看起来像一个消息队列功能，实际上是三个问题：

- 用流式输入建立运行中的消息通道；
- 用权威生命周期事件判断何时真正结束；
- 用应用层状态门控封住 abort 和审批附近的竞态。

**能把消息送进去，不等于消息一定会被处理。** 对 agent bot 来说，真正可靠的交互不是“接收成功”，而是每条消息都进入了一个仍有能力完成它的生命周期阶段。
