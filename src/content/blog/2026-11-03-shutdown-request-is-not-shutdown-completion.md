一段定时关机脚本按时执行，`osascript` 退出码也是 `0`，但第二天机器还开着。

第一眼很容易把问题归到调度器：是不是定时任务没触发、权限不够，或者脚本被系统杀了？日志还原出的真实过程却是：关机请求已经送达，随后一个仍有未完成状态的图形应用取消了关机。

这里最重要的教训不是“记得先关某个应用”，而是：**请求被接受，只能证明控制信号发出成功，不能证明目标状态已经达成。**

## 🧩 图形化关机是协作流程

通过 System Events 发起关机，本质上走的是 macOS 的图形会话关机流程。系统会要求各个应用退出；应用可能因为未保存内容、正在通话、后台任务或自身策略而拒绝退出。

因此，下面三件事必须分开看：

1. 定时任务是否准时启动；
2. AppleScript 是否成功提交关机请求；
3. 系统是否最终完成关机。

`osascript` 返回 `0` 只覆盖前两层。应用稍后取消关机时，发起命令的进程可能早已正常结束。拿退出码当最终验收，就会得到一个“日志全绿、机器没关”的假成功。

## 🔎 日志要记录状态链，而不是一句 success

单行日志“shutdown command succeeded”几乎没有诊断价值。更有用的是把关键状态拆开记录：

```text
08:05:16 scheduler fired
08:05:16 shutdown request submitted
08:05:17 application rejected termination
08:06:16 machine still running, retry 1/3
```

如果系统日志能看到具体应用返回取消信号，就应保留应用类型和错误类别；公开日志则对应用名、用户名和路径做脱敏。

这类状态链能立刻回答三个问题：调度有没有执行、请求有没有发出、是谁阻止了结果。

## 🛡️ 更可靠的关机脚本需要三道门

### 1. 处理已知阻塞者

在无人值守、且设备用途明确的环境里，可以先关闭经过允许的已知阻塞应用，再发送关机请求。

这里必须使用 allowlist（允许清单），不能粗暴结束所有 GUI 进程。强制退出可能造成未保存数据丢失，适合的是可恢复、无重要编辑状态的应用；其他应用应先尝试正常退出，并设置超时。

### 2. 验证“机器仍然活着”

请求发出后等待一段时间。如果脚本还能继续运行，或外部探针仍能访问主机，就说明关机没有完成。

验证指标要对准业务目标：

- 错误指标：命令退出码为 `0`；
- 正确指标：主机进入关机流程并最终离线；
- 辅助指标：登录会话结束、网络服务停止、下一次启动时能看到上次关机记录。

脚本运行在被关闭的机器上时，成功路径天然不会留下“我已关机”的最后一行日志。需要强证明时，应由另一台设备或远程监控承担最终确认。

### 3. 有界重试，而不是无限循环

检测到机器仍在运行后，可以重新处理阻塞者并再次请求关机，但必须限制次数，例如间隔 60 秒、最多 3 次。

有界重试同时解决两个问题：

- 临时阻塞有机会自行解除；
- 永久阻塞不会让脚本无限循环或反复打断用户。

达到上限后，应记录明确失败，并保留最后一次已知阻塞原因。

## 🧪 验收要故意制造一次阻塞

只在“所有应用都愿意退出”的顺路径测试，无法证明修复有效。至少要覆盖：

1. 没有阻塞应用时能正常关机；
2. 一个测试应用拒绝退出时，脚本能识别机器仍在线；
3. 已知阻塞者被安全关闭后，重试能继续；
4. 未知阻塞持续存在时，脚本在上限处停止并留下可诊断日志；
5. 脚本重复触发时不会启动多组关机循环。

尤其是第二项，它验证的不是某个应用，而是整套自动化有没有区分“请求成功”和“结果成功”。

## ✅ 结论

操作系统自动化里，命令退出码通常只属于控制面；用户真正关心的是状态面。

定时任务触发了、AppleScript 返回了、日志写了 success，都不能代替“机器确实关机”这一业务结果。可靠方案必须把链路拆开：**处理阻塞者、发出请求、等待结果、有界重试、外部确认。**

这套原则也适用于重启服务、卸载应用、部署网站和发送消息：API 接受了动作，不代表现实世界已经变成你要的状态。
